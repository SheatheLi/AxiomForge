# 研究与工程结果｜真实问题、竞争方法和可证伪边界

## 根本问题

异步服务中的**状态提交时序（commit timing）与取消清理语义**：一个对象先把自己标记为关闭，随后才异步改变真实连接状态；如果第二次取消在内部 `await` 处中断，后续请求看到“已关闭”的逻辑标志，不会再执行真正的状态回收。外部现象是连接池不断累积活动连接，服务最终因容量耗尽而阻塞。

这比“能够在 await 处注入取消”有更大工程价值，因为给出了具体源码缺陷、修复候选和针对真实库的可重复对照。

## 外部真实来源

- HTTPX #3782：https://github.com/encode/httpx/issues/3782 。已报告并公开复现的双次取消问题，不是本项目首次发现。
- HTTPcore #1113：同一失效机制关联的上游问题；任何修复需审查真实合并状态。
- SQLAlchemy #13548：https://github.com/sqlalchemy/sqlalchemy/issues/13548 。连接初始化失败导致 DBAPI 对象未被明确关闭，连接池配额健康仍不足以代表物理资源健康。
- SQLAlchemy #12460：https://github.com/sqlalchemy/sqlalchemy/discussions/12460 。驱动事务与连接池状态失配可诱发锁积累。

## 外领域的可迁移思想与实际采用程度

| 来源领域 | 方法 | 本版实际采用 | 没有实现 / 不可宣称 |
|---|---|---|---|
| 事务与 C++ 强异常安全 | “先完成资源状态转换，再提交完成标志”；失败后支持回滚重试 | 对比 early-commit、defer-commit、rearm 三种时序；确认前移标记的具体失效 | 并非所有外部副作用都可事务性回滚 |
| 分布式请求去重 | Single-flight，同一 key 的并发调用共享一次进行中执行 | `singleflight-commit` 用同一个 AsyncIO Task 承接关闭，防止双并发关闭 | Trio/跨 Event Loop 与取消生命周期未完整证明；不是发明 Single-flight |
| 形式化方法 | 有限状态探索和最短反例 | 在单连接/两次关闭尝试的抽象模型上 BFS 完整枚举；一次取消、两次尝试时 bad terminal 从 1 降到 0 | 不证明真实运行时所有 interleaving；两次尝试都被取消时，defer 仍可失败 |
| 运筹学/组合优化 | 0–1 MILP 加权 Hitting Set | SciPy HiGHS 求解给定多个恢复路径的最小候选中断集；测试对照穷举最优 | 还未从 HTTPX 自动学习可靠的替代恢复路径；优化输出并不保证在真实代码中触发失败 |
| LDFI / Molly | 从目标结果逆向考虑哪些依赖可以被故障切断 | 只借鉴问题选择和干预解释方式，结合现有资源协议事件 witness | 没有实现 Molly 的 Dedalus/完整 SAT lineage 引擎 |
| Jepsen | 把操作历史的收集与检查规则分离 | v1.5 以来的资源事件检查与真实运行对照 | 未实现通用分布式线性化检查器 |

## 有意义的反对照

- **原实现：** 0→1→2→3 活动连接，第 4 轮超时。
- **仅 CancellationShield：** 结果不变，因此否定“只要加屏蔽就能修”的简单推断。
- **恢复关闭标志：** 0/4 活动残留，成功；需要真实调用方重试。
- **完成后再标记：** 0/4 活动残留；但两个并发关闭调用会两次进入底层 `_response_closed()`，会造成新的竞态。
- **Single-flight + 完成后标记：** 本地真实库对照 0/4 活动残留、0 次阻塞；人工并发双调用中底层只调用 1 次。该技术路径从请求合并思想迁移到资源最终化，依然需要继续验证异常、取消传播、后端兼容和任务存活。
- **真实补丁 Diff：** rearm 版本仅修改 `HTTP11ConnectionByteStream.aclose` 的失败路径；完整 `patch --dry-run` 通过、在临时复制出的 HTTPcore 真实源码应用并使用独立进程，四轮双次取消全无残留。

### 证据是哪个数字、具有什么分母

主要结果以 `benchmarks/reliability/live_results.json` 的 `strategies[*].rows`、`patched_process_results.json` 与测试源码为准。这是一个确定版本、固定连接上限、单机 loopback、时序敏感、没有公网的真实故障复验，不是随机抽样估计整行业修复率。采用相同 4 轮 × 5 策略 × 2 取消模式，样本为**40 个单次场景迭代/尝试**，部分存在提前终止。不能将这些次数等价为独立工业缺陷数，也不能当成无偏随机抽样。

SQLAlchemy 的跨层事件实验为 5 次初始化失败、5 个未退役账本记录，对照人工释放 0 个，健康池 0 个。使用 SQLite，没有证明远端 PostgreSQL/Oracle 连接数或真实会话泄露。

MILP demo 的 8→4 是人工给定路径的最小成本，不是降低了 50% 真实故障搜索成本。

## 当前必须停止的虚假主张

- 无法声称“实现原创通用 DPOR/符号执行/SMT 约束求解/大规模工业修复”。
- 无法声称已向 HTTPcore 提交 PR、已被维护者接受、已在企业生产环境部署。
- 无法把对一个公开 Issue 的真实修复候选等价为自动化解决多个未见缺陷。
- 无法把 4 次连续成功等价为可靠性百分百，更不能忽视另一个 asyncio 调度环境、Trio 和高并发竞争。

## 对应真实高压评价

已达到**真实复杂对象的源码级机制分析、多个技术结构之间的实验性竞争、可应用补丁、真实库对照、并发反例发现**。相比 v1.5 从“故障检测”前进到“源代码修复与机制验证”。

没有达到**开创性新算法、等预算领先成熟修复框架、未见问题的广域效果、上游外证/合并、学习者独立 Ownership**。求职可使用的陈述必须以局部真实工程成果为边界。
