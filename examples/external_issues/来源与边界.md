# 公开问题、独立实证与边界

该目录的数据可离线运行，是根据公开报告提供的实例、条件与可描述故障**分别重建的 SQLite 语义场景**。它们不是上游仓库的原始测试套件，也不是在 Trino、Redshift、Snowflake 或 dbt Fusion 上执行的端到端复现。公开问题的历史状态（包括已关闭或已修复）不应被描述为我们修复了上游。

## 复合键交叉组合误删除

- 来源：[dbt-core #11799](https://github.com/dbt-labs/dbt-core/issues/11799)
- 证据等级：**报告给出 SQL 错误形式、完整小表构造和正确替代 SQL；在 SQLite 上忠实重现同一关系逻辑。**
- 具体问题：错误的条件把多个键列分别放入 `IN (SELECT ...)`，相当于对各列允许值做笛卡尔积，删除了阶段表中并不存在的组合。
- 当前数据：目标 13 行，阶段 13 行。错误语句删除 13 行，完整键只匹配 7 行，多删除 6 行。
- 反例：精确保持错误目标键 `(8, 'tst')`，独立缩减到 1 行目标 + 2 行阶段。
- 负向对照：`composite_fixed.sql` 使用完整复合键元组匹配，审查 PASS。
- **增量对照**：两表复合键均无重复、均无 NULL，简单唯一性与非空检测通过；实际执行 DELETE 的完整元组级影响分析仍发现 6 行误删除。不能据此声称超越 dbt 所有自定义 SQL 测试。

## 增量键含 NULL

- 来源：[dbt-core #5691](https://github.com/dbt-labs/dbt-core/issues/5691)，另参见 [dbt 官方增量模型说明](https://docs.getdbt.com/docs/build/incremental-models)。
- 证据等级：**按报告中 day-1/day-2 的关键数据行重建 NULL 匹配机制；并未运行 Redshift。**
- 表现：目标含 `(NULL, onion, 5)`，增量阶段含 `(NULL, onion, 7)`。普通 SQL `=` 不匹配两个 NULL，增量模型可能产生重复记录。
- 工具输出 `NULL_KEY`、`NULL_MATCH_GAP`；显式选择 `--null-safe` 后还会发现非 NULL-safe 实现的 `MISSED_DELETE`。
- 对照：`nullable_fixed.sql` 使用 SQLite 的 `IS` 运算，在显式 NULL-safe 合同下 PASS。实际 dbt 工程还需核对具体 adapter、唯一键与建模方案。非空检测也可发现本类问题，并非独家能力。

## 多个源记录匹配同一目标行

- 来源：[dbt-core #10432](https://github.com/dbt-labs/dbt-core/issues/10432)。
- 证据等级：**合成的、从问题描述推导的故障机制**；报告者声明其键已经检查唯一，未提供仓库数据和可复现输入；**不能宣称复现或修复了该 Issue 的实际根因**。
- 诊断：`MULTIPLE_SOURCE_MATCH` 要求同一键对应至少两条阶段源记录且至少一条目标记录；反例为 1 行目标 + 2 行源。只存在阶段重复但没有目标匹配时，不足以构成这个具体 MERGE 冲突指纹。
- 标准 `unique` 测试也能够检测源键重复；这一测试的贡献是区分“源本身重复”和“同一目标被多个源匹配”，并在提取反例时保持目标存在。

## 微批次源侧时间过滤缺失

- 来源：[dbt Fusion #14525](https://github.com/dbt-labs/dbt/issues/14525)，后续讨论曾将范围收窄到时区谓词渲染差异，相关修复已合并。
- 证据等级：**按报告中的 10 条数据、4 个批次、40 条最终输出的现象构造独立离线数据库**；实际日期和记录内容由本项目生成，**不是 Snowflake 或 Fusion 运行证据**。
- 过程：每个批次读取全量 10 条源记录，累计 40 行；动态执行 `microbatch_bug.sql` 在四个窗口下产生 `SOURCE_WINDOW_LEAK` 与 `MULTIBATCH_DUPLICATED`。
- 对照：`microbatch_fixed.sql` 使用 `:start`、`:end` 限制源侧读取，累计只读 10 行，PASS。
- 重要边界：本项目仅验证**明确声明必须逐窗口读取的源侧 SQL 合同**。dbt 某些未声明 `event_time` 的上游模型，全量扫描属于正常预期，不能一概视为 Fusion bug；目前只支持日期文本，不具备 Snowflake 时区会话一致性验证。

## 分区键不等于逐行唯一主键（负向控制）

- 来源：[dbt-core #11397](https://github.com/dbt-labs/dbt-core/issues/11397)。
- 证据等级：**根据公开设计讨论构造的正常业务场景**，并非上游 BUG 复现。
- 分区覆盖以 `date_day` 为键，允许同一天的多条不同 event 行；按 `--grain partition` 进行完整分区删除，PASS；如果错误地按 `--grain row` 要求每个分区键唯一，便会误报。
- 意义：一个只会检查 uniqueness、完全不考虑合同语义的守门器，会误伤合法增量任务。

## 复现与独立性

项目根目录：

```bash
python 验证外部问题.py
```

会生成三个独立证据 ZIP、四类公开问题诊断与四个修正或正常对照，以及 `validation.json` 原始记录。三个 ZIP 各自包含实际缩减的数据库、候选 SQL、错误指纹、校验哈希以及只依赖 Python 标准库的 `replay.py`。审计脚本会在新目录解压运行重放器，对最小性进行另外一轮单行删除尝试，且检查原始数据库哈希没有变化。

这些证明的是**在指定 SQLite 故障模型下，算法真正工作、反例可独立复现**，不是实际替第三方维护者修复了软件。向外部开发者分享实际数据库前，应先处理隐私和敏感数据，项目本身不进行自动脱敏。
